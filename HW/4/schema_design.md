## Система бронирования отелей (Вариант 13)

## Коллекции

Система содержит три коллекции: **users**, **hotels**, **bookings**.

---

## Структура документов

### Коллекция `users`

```json
{
  "_id":          ObjectId,
  "login":        "ivan_petrov",
  "password_hash":"$2b$12$...",
  "first_name":   "Иван",
  "last_name":    "Петров",
  "email":        "ivan@mail.ru",
  "created_at":   ISODate("2025-01-01T00:00:00Z")
}
```

### Коллекция `hotels`

```json
{
  "_id":             ObjectId,
  "name":            "Marriott Москва",
  "city":            "Москва",
  "address":         "Тверская ул., 26",
  "stars":           5,
  "rooms_total":     340,
  "price_per_night": 15000.0,
  "amenities":       ["WiFi", "Парковка", "Бассейн", "Спа"],
  "created_at":      ISODate("2025-01-01T00:00:00Z")
}
```

### Коллекция `bookings`

```json
{
  "_id":        ObjectId,
  "user_id":    ObjectId,
  "hotel_id":   ObjectId,
  "hotel_snapshot": {
    "name":            "Marriott Москва",
    "city":            "Москва",
    "price_per_night": 15000.0
  },
  "check_in":    ISODate("2025-06-01T00:00:00Z"),
  "check_out":   ISODate("2025-06-05T00:00:00Z"),
  "nights":      4,
  "total_price": 60000.0,
  "status":      "confirmed",
  "created_at":  ISODate("2025-05-01T00:00:00Z")
}
```

## Обоснование выбора embedded vs references

### users — отдельная коллекция (references из bookings)

**Решение:** хранить пользователей отдельно, ссылаться на них по `user_id`.

**Обоснование:**
- Пользователи запрашиваются независимо: поиск по логину, по маске имени/фамилии.
- Данные пользователя изменяются (email, пароль) — при embedded пришлось бы обновлять вложенный объект во всех бронированиях.
- Один пользователь может иметь много бронирований — дублирование данных нецелесообразно.

### hotels — отдельная коллекция (references из bookings) + частичный snapshot

**Решение:** хранить отели отдельно; в документ бронирования встраивать `hotel_snapshot` с именем, городом и ценой за ночь.

**Обоснование:**
- Отели запрашиваются независимо (список отелей, поиск по городу) — требуется отдельная коллекция.
- `hotel_snapshot` в бронировании — денормализация для производительности: при загрузке списка бронирований не нужен $lookup к hotels.
- Цена может меняться, но в бронировании зафиксирована историческая цена — snapshot корректен семантически.
- Поле `amenities` (массив строк) встроено в отель — это его неотъемлемое свойство, не имеющее смысла вне контекста отеля и не обновляется независимо.

### bookings — отдельная коллекция

**Решение:** отдельная коллекция, а не массив в документе пользователя.

**Обоснование:**
- Неограниченный рост (anti-pattern "unbounded array"): пользователь может иметь тысячи бронирований — MongoDB имеет лимит 16 МБ на документ.
- Бронирования запрашиваются по разным критериям: по пользователю, по отелю, по дате, по статусу.
- Отмена/изменение статуса — атомарная операция на отдельном документе.

## Индексы

| Коллекция | Поле(я) | Тип | Причина |
|---|---|---|---|
| users | login | unique | быстрый поиск при логине |
| users | email | unique | уникальность |
| users | first_name, last_name | text | полнотекстовый поиск по маске |
| hotels | city | 1 (ascending) | поиск по городу |
| hotels | stars | 1 | фильтрация по звёздности |
| bookings | user_id | 1 | брони пользователя |
| bookings | hotel_id | 1 | брони отеля |
| bookings | (user_id, status) | 1, 1 | активные брони пользователя |
| bookings | check_in | 1 | отчёты по датам |
